MICROSERVICE MIGRATION ROADMAP
===============================

Purpose
-------
Turn this FastAPI/LangGraph customer-support assistant into independently deployable
services without breaking the existing frontend/API behavior. Use a gradual
"strangler" migration: keep the current backend operating while each bounded
capability is extracted and tested.

Migration constraints
---------------------
* Preserve the frontend-facing authentication, ticket, booking, conversation,
  and chat contracts until each replacement has passed contract and parity
  checks.
* Keep the supported assistant scope limited to company-policy questions,
  ticket and booking requests, IT support, and harmless pleasantries. Web
  search and a web-tools service are out of scope.
* Preserve authenticated owner and thread isolation across every extraction.
  Customer name and email for ticket/booking creation come from trusted
  identity claims, never LLM-generated values.
* Preserve durable HITL behavior: pending actions have an owner, thread,
  expiry, decision state, and idempotency protection. Completed work from a
  multi-request message must remain visible when another action awaits approval.
* Persist timestamps in UTC and present customer-facing dates in ICT (UTC+7).
* Do not make the migration dependent on a request-time RAG index build or
  model download. Each service must have explicit health, readiness, logs,
  metrics, deadlines, and rollback behavior before traffic moves.

Target architecture
-------------------
Client -> API gateway/BFF -> chat-orchestrator -> domain services
                                  |               |-- knowledge-rag
                                  |               |-- ticket
                                  |               |-- booking
                                  |               |-- it-support
                                  |               |-- memory
                                  |               |-- identity (or existing auth)
                                  |
                                  +-> workflow/checkpoint store

All external traffic enters the gateway. The gateway validates JWTs, applies
rate limits, and forwards identity headers/tokens. The chat-orchestrator owns
LangGraph routing, supervisor logic, tool/HITL state, and final response
assembly. Domain services own their business data and expose stable APIs. Use
an event broker for facts that do not need an immediate response (for example,
ticket-created, booking-created, memory-requested, audit events).

Recommended first deployment stack
----------------------------------
* Containers: Docker Compose locally; Kubernetes only after service boundaries
  and operational needs are proven.
* Gateway: Traefik, Kong, or an existing company ingress/API gateway.
* Databases: PostgreSQL. Start with one PostgreSQL cluster but give every
  service its own database/schema, credentials, migrations, and tables.
* Async transport: RabbitMQ, NATS, or Kafka. RabbitMQ is a sensible first
  choice for this workload; do not introduce a broker until an extracted flow
  needs asynchronous delivery.
* Caches/locks: Redis for rate limiting, short-lived conversation locks,
  idempotency keys, and optional response caching.
* RAG: object storage for PDFs/index artifacts and a dedicated vector store
  (pgvector is a simple initial choice; Qdrant is a good dedicated option).
* Observability: OpenTelemetry traces, structured JSON logs, Prometheus metrics,
  and a centralized log backend. Propagate a correlation ID from the gateway
  through every request and event.

Phase 0 - establish a safe baseline
-----------------------------------
1. Document every public endpoint, request/response model, authentication rule,
   table, LangGraph node, tool, external API, and background side effect.
2. Add integration tests for login, chat routing, FAQ/RAG, ticket creation,
   booking creation, HITL approve/reject, conversation history, and memory.
3. Add contract tests for the frontend-facing REST API, beginning with /chat,
   /tickets, /bookings, and auth. Keep these contracts stable through migration.
4. Add health (/health), readiness (/ready), and version endpoints, structured
   logs, request IDs, and metrics to the monolith.
5. Define SLOs such as chat availability, p95 response time, tool failure rate,
   RAG retrieval latency, and confirmation completion rate. Capture current
   values as the baseline.

Phase 1 - repair configuration and persistence before extraction
-----------------------------------------------------------------
1. Change database.py to read DATABASE_URL. Retain SQLite only as an explicit
   local-development default, not as an unintentional production fallback.
2. Introduce Alembic migrations; do not use Base.metadata.create_all() as the
   production schema migration mechanism.
3. Move app data from SQLite to PostgreSQL. Validate row counts, foreign keys,
   passwords, timestamps, and per-user/thread access after migration.
4. Move LangGraph checkpoints from local checkpoints.db to a production-safe,
   shared checkpointer/store. Ensure multiple orchestrator replicas can resume
   the same thread correctly.
5. Replace local FAISS and mounted PDF assumptions with versioned artifacts in
   object storage. Keep index build/version metadata so queries use a known
   document/index version.
6. Put secrets in a secret manager or deployment secrets; remove credentials
   from Compose defaults in production. Add config validation at startup.

Phase 2 - modular monolith boundaries
--------------------------------------
1. Keep one deployable backend, but reorganize modules by capability:
   identity, chat-orchestration, ticket, booking, knowledge, memory, IT support,
   and shared platform libraries.
2. Define interfaces at each boundary. The orchestrator must call interfaces,
   not directly import ticket_tools, booking_tools, CRUD modules, or SQLAlchemy
   models from another capability.
3. Separate shared code into small versioned packages only for genuinely common
   concerns: API contracts, authentication claims, observability, error format,
   and event envelope. Do not create a large shared business-model package.
4. Make every mutation idempotent. Accept an Idempotency-Key on ticket and
   booking commands; persist the result keyed by authenticated user and key.
5. Model HITL explicitly: persist a pending action with action ID, actor,
   thread ID, expiry, desired operation, approval status, and idempotency key.
   Approval/rejection must be safe to retry and must never trust client-supplied
   owner IDs.

Phase 3 - extract the knowledge service first
----------------------------------------------
1. Define a versioned internal knowledge API contract.
   - POST /v1/query accepts a query, minimal authenticated requester claims,
     correlation ID, and optional approved index version.
   - Return answer-ready passages, scores, citations, retrieval/index version,
     and a machine-readable unavailable/degraded result.
   - The chat orchestrator remains responsible for routing, guardrails, final
     wording, HITL, and combining results from multi-request messages.

2. Extract knowledge-rag behind the existing knowledge adapter.
   - Keep a local implementation and add an HTTP implementation behind the
     same interface, selected with configuration or a feature flag.
   - Deploy the service with internal-only networking and service-to-service
     authentication. Forward minimal claims and correlation ID; do not forward
     passwords, raw JWTs, or unnecessary PII.
   - Add deadlines, safe-read retries, circuit breaking, and a plain-language
     fallback for unavailable dependencies.

3. Transfer knowledge ownership.
   - The service owns ingestion, chunking, embeddings, index/version metadata,
     retrieval, reranking, and citation metadata.
   - Run ingestion asynchronously. Serving a query must not build an index or
     download a model on the request path.
   - Store source documents and versioned artifacts in object storage. Record
     checksum, model/version, creation time, and activation status so each
     answer is traceable to an approved artifact version.
   - Do not let the knowledge service access ticket, booking, memory,
     pending-action, conversation, or checkpoint tables directly.

4. Preserve product boundaries during the rollout.
   - Knowledge answers only approved company-policy questions. Return an
     unavailable result when retrieval is insufficient; do not answer from
     general knowledge.
   - Do not add or extract a web-tools service: the web agent is out of scope.
   - Keep IT support in the orchestrator for now. It can be extracted later
     only when it has independent integrations, ownership, or scaling needs.
   - A completed lookup must remain visible when a later ticket or booking
     action pauses for confirmation in the same user message.

5. Verify before switching traffic.
   - Add local-versus-HTTP contract tests for citations, index-version
     propagation, policy-only behavior, timeouts, and degraded responses.
   - Shadow a privacy-safe sample of policy queries through both paths; compare
     passages, citations, safety decisions, and latency.
   - Monitor correlation IDs, latency, error/degraded rate, artifact version,
     citation coverage, and fallback rate. Roll back by changing the adapter
     flag until parity is demonstrated.

Phase 4 - extract transactional domain services
------------------------------------------------
1. Extract ticket service.
   - Own ticket data, validation, allowed status transitions, audit history,
     and ticket command/query APIs.
   - Preserve idempotency keyed by authenticated subject and Idempotency-Key.
   - Resolve customer name and email from trusted identity claims on creation;
     never trust LLM-generated identity fields.
   - Publish TicketCreated and TicketUpdated events through a transactional
     outbox, not a direct broker write from request code.

2. Extract booking service.
   - Own booking data, availability validation, booking lifecycle, audit
     history, and command/query APIs.
   - Keep availability checks and the booking commit in one transactional
     operation. Apply the same authenticated-subject idempotency behavior.
   - Store timestamps in UTC and return unambiguous ISO timestamps. The
     frontend/orchestrator presents customer-facing time in ICT (UTC+7).
   - Publish booking events through its own transactional outbox.

3. Extract memory service.
   - Own semantic and episodic memory, retrieval policy, retention, deletion,
     and privacy controls.
   - Provide synchronous retrieval for a chat turn and asynchronous recording
     for completed interactions. Ensure deletion and retention apply to all
     memory representations.

4. Isolate data and authorization.
   - Give each extracted service a private schema/database, credentials,
     migrations, backups, and restore procedure.
   - Other services access domain data only through APIs or events; do not join
     another service's tables.
   - Re-authorize every command against the authenticated subject. Retain
     owner and thread isolation tests for tickets, bookings, and pending work.

5. Migrate incrementally.
   - Put remote ticket, booking, and memory adapters behind feature flags.
   - Reconcile records and side effects during shadow/canary traffic. Verify
     idempotency replay/conflict, retry, expiry, and rollback behavior before
     retiring each monolith implementation.

Phase 5 - extract the chat-orchestrator
----------------------------------------
1. Create a chat-orchestrator service containing AgentState, guardrail,
   context, router, supervisor, LangGraph definition, HITL coordination, and
   adapters for knowledge, ticket, booking, memory, and IT support.

2. Expose POST /v1/chat/messages.
   - Input contains message and optional client-generated thread ID. Identity
     comes only from validated gateway claims.
   - Return answer, selected route, thread ID, pending-action information, and
     correlation ID.
   - Preserve multi-request semantics: complete safe lookups, retain their
     results, and return any later confirmation without losing completed work.

3. Expose POST /v1/pending-actions/{id}/decision.
   - Authorize by persisted action owner and thread, not request-body IDs.
   - Make approve, reject, expiry, and repeated decisions idempotent and safe
     across retries.

4. Externalize workflow state safely.
   - Store checkpoints and pending actions outside pods. Use an optimistic
     version or per-thread lock to prevent simultaneous turns from corrupting
     state.
   - Ensure restart and multi-replica recovery tests cover pending actions,
     multi-request turns, owner isolation, and thread isolation.

5. Maintain compatibility during adoption.
   - Keep the current /chat endpoint as a compatibility adapter until the
     frontend uses the gateway route.
   - Shadow selected traffic and compare route, safety decision, tool calls,
     completed results, confirmations, and side effects before shifting traffic.

Phase 6 - gateway, events, and production rollout
--------------------------------------------------
1. Route public traffic through the gateway and make service endpoints private.
   Centralize CORS, JWT verification, request-size limits, rate limits, API
   versioning, and correlation-ID propagation.

2. Standardize cross-service behavior.
   - Use common error responses, deadlines, pagination, authenticated claim
     propagation, and observability fields.
   - Each service must authorize sensitive operations itself even after gateway
     validation.

3. Define a versioned event envelope.
   - Include event_id, event_type, occurred_at, producer, schema_version,
     correlation_id, causation_id, and minimal payload.
   - Use durable consumers with event-id deduplication. Never place raw secrets
     or unnecessary customer PII in events, prompts, logs, or traces.

4. Operate the transactional outbox.
   - Publish ticket and booking domain events from an outbox worker after the
     business transaction commits.
   - Monitor outbox age, failed deliveries, duplicate handling, and consumer
     lag. Do not use distributed database transactions.

5. Establish delivery and recovery controls.
   - Run per-service unit, integration, contract, security, container, and
     migration tests in CI/CD. Promote immutable image tags through
     environments.
   - Use canary or percentage rollout, dashboards, alerts, backups, restore
     drills, and a rollback plan that keeps database/API compatibility.
   - Remove monolith paths only after traffic, data reconciliation, and the
     rollback window demonstrate parity.

Service ownership and interfaces
--------------------------------
Service              Owns                                      Sync interface
identity             users, credentials, JWT issuance          login/refresh/JWKS
chat-orchestrator    graph state, routing, HITL, response       chat + decision APIs
knowledge-rag        documents, indexes, retrieval metadata     query API
ticket               tickets and ticket audit trail             ticket command/query API
booking              bookings and booking audit trail           booking command/query API
memory               semantic/episodic memories and policy      retrieve/write/delete API
it-support           IT-specific integrations/data (if needed)  support action/query API

Security and reliability requirements
-------------------------------------
* Use service-to-service authentication (mTLS, workload identity, or signed
  internal JWTs); never rely only on private-network placement.
* Propagate authenticated subject, scopes, and correlation ID. Each service
  re-authorizes sensitive operations against its own owned resource.
* Never send raw secrets, passwords, or unnecessary PII in events, prompts,
  traces, or logs. Encrypt data in transit and at rest.
* Apply strict input/output validation around LLM prompts and tool arguments.
  Keep guardrails in the orchestrator and enforce business validation again in
  domain services.
* Set deadlines, bounded retries with jitter, circuit breakers, bulkheads, and
  clear fallback messages for every remote dependency.
* Back up PostgreSQL and vector/document stores; periodically test restoration.

Definition of done
------------------
* Every service can be built, tested, deployed, scaled, and rolled back
  independently.
* No service reads or writes another service's database directly.
* Chat turns, checkpoints, pending approvals, and idempotent mutations survive
  process restarts and multiple replicas.
* Frontend API contracts and authorization behavior remain compatible.
* Distributed traces show a chat request through orchestrator, tools, events,
  and domain services; dashboards and alerts cover the defined SLOs.
* The old monolith paths are removed only after traffic, data reconciliation,
  and rollback windows demonstrate parity.

Suggested implementation order
------------------------------
1. Configuration/PostgreSQL/Alembic/checkpointer/observability.
2. Internal capability interfaces and contract tests.
3. knowledge-rag.
4. ticket, booking, and memory services with private databases and outboxes.
5. chat-orchestrator and durable HITL workflow state.
6. Gateway rollout, traffic migration, then deletion of monolith code.
